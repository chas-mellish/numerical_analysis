# Chapter 1, Program 1: Interval halving (bisection)

*Book page 24, "Solution of Nonlinear Equations". Catalog entry: `catalog/ch01_p01_bisection.toml`.*

## The method

Interval halving finds a root of F(X) = 0 inside an interval [X1, X2] where F changes sign.
If F is continuous and F(X1)·F(X2) < 0, there must be a root between X1 and X2. Each pass:

1. computes the midpoint X = (X1 + X2)/2 and F(X);
2. stops if |F(X)| ≤ TOL;
3. otherwise keeps the half that still has a sign change: if F(X)·F(X1) < 0 the root lies in
   [X1, X], so X2 = X; if the product is positive the root lies in [X, X2], so X1 = X and
   F(X1) = F(X).

The bracket halves on every pass, so after k passes it is (X2 − X1)/2^k wide. Convergence is slow
(one binary digit per pass) but guaranteed, which is why bisection is the safe fallback for the
faster methods later in the chapter.

Two details of Gerald's program are worth noticing:

* **The stopping test is on the residual |F(X)|, not on the width of the interval.** A small
  residual does not mean X is close to the root when F is flat. A steep F can also need many
  passes before |F(X)| gets small.
* **The program gives up after 25 halvings** (`DO 30 I = 1, 25`) and prints
  `NON-CONVERGENT IN 25 ITERATIONS.`

## The book's data card

The function is fixed by a statement-function card, `F(X) = EXPF(-X) - SINF(3.1415926*X/2.)`. The
data card, read with `FORMAT (2F10.0, E10.0)`, holds X1, X2 and TOL:

```
0.        1.        1.E-5
```

F(0) = 1 and F(1) = e⁻¹ − 1 ≈ −0.632, so [0, 1] brackets a root. The book's output:

## Other outcomes the program handles

| Situation | Book output | Modern behaviour |
|---|---|---|
| F(X1) and F(X2) have the same sign | `FUNCTION VALUES WITH INITIAL X VALUES ARE NOT OF OPPOSITE SIGNS. CHANGE INPUTS.` | `BracketError` (trace code `BRACKET`) |
| X1 or X2 is already a root | `THE INPUT VALUE, X = …  IS A ROOT OF THE EQUATION.` (F6.3) | result with `root_at_endpoint`, 0 iterations |
| F(X1)·F(X2) tests zero but neither value is zero (underflow) | `ERROR. FX1 AND FX2 NOT ZERO THOUGH PRODUCT TESTS ZERO.` | `ZeroProductError` (`ZERO_PRODUCT`) |
| F(X)·F(X1) is exactly zero during the halving | `ERROR.` | `ZeroProductError` (`ZERO_PRODUCT`) |
| 25 halvings without \|F(X)\| ≤ TOL | `NON-CONVERGENT IN 25 ITERATIONS.` | `NonConvergenceError` (`NON_CONVERGENT`) |
| F(X1), F(X2) or F(X) is NaN or infinite (EXP(−X) overflows for X < −709 in real64 and X < −88 in real32; or a learner function) | — (impossible on the original machine) | `InputError` (trace code `INPUT`, exit status 2; without `--trace` a message on stderr and exit status 1), with the rows computed so far |

A successful run ends with one trace record
`RESULT,value=…,converged=T,iterations=…,root_at_endpoint=T|F,fx1=…,fx2=…`: besides the root and
the iteration count it reports whether X1 or X2 was already a root (`root_at_endpoint`, then
`iterations=0` and the book's FORMAT 201 line) and F(X1), F(X2) at the data card's X1 and X2
(`fx1`, `fx2`; they decide which input value FORMAT 201 reports). The web page lists them under
"Result details".

## Precision

The book ran in single precision. In this problem the precision hardly matters:

* every midpoint is a dyadic fraction (0.5, 0.25, 0.375, …), exact in both real32 and real64, so
  the X column is identical in both;
* F(X) differs by about 1e-7 (row 15: 9.99e-7 in real64, 1.07e-6 in real32). Both print as
  `.000001`, and both runs stop after 15 iterations at X = 0.443572998046875.

The visible differences come from the printer. It **truncated** the last digit and dropped the
leading zero, so 0.44140625 printed as `.4414062`. A modern compiler rounds and prints `0.4414063`.
The golden tests therefore compare X within 1e-7 and F(X) within 1e-6 instead of comparing text. The
book's truncated π (3.1415926) is kept: it is part of the book's F(X).

Which computer produced the printout is not known (see `docs/architecture.md`, "The book's
computer"). The `ZZJOB` and `ZZFORX` deck-control cards on this page look like IBM 1620 Monitor
cards, which points to 8-digit decimal floating point with chopped results, and the Bairstow
program's coefficient echo (`ch01_p02`) also suggests a decimal machine. The Chapter 3 sums
(`ch03_p01`, `ch03_p02`) are better explained by 27-bit chopped binary arithmetic (IBM 7090
class). This program cannot settle the question: the F(X) digits that the real64 build (row 15)
and the real32 build (row 11) each miss by one unit are reproduced by both a decimal and a binary
chopped emulation.

Precision starts to matter when TOL approaches real32 resolution (about 6e-8 near X = 0.44). In our
checks, with TOL = 1.E-7 a real32 run stops after 23 iterations and a real64 run after 24. With
TOL = 1.E-9, real64 reports `NON-CONVERGENT IN 25 ITERATIONS.`, while real32 stops after 24 because
its rounded F(X) happens to fall below TOL. Try this with the Fortran `SINGLE` build.
