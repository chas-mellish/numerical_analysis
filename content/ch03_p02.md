# Chapter 3, Program 2: Romberg integration, Si(B)

*Book page 74, "Numerical Integration". Catalog entry: `catalog/ch03_p02_romberg.toml`.*

## The method

The trapezoidal rule with step h has an error that is a series in even powers of h:

T(h) = I + c₁h² + c₂h⁴ + c₃h⁶ + …

If T(h) and T(h/2) are both known, the combination T(h/2) + (T(h/2) − T(h))/3 cancels the h² term
(this is Simpson's rule). Combining two such values with the factor 1/15 cancels the h⁴ term, and
so on. **Romberg integration** repeats this Richardson extrapolation systematically in a
triangular table:

TRAP(II+1, I+1) = TRAP(II, I+1) + (TRAP(II, I+1) − TRAP(II, I)) / (4^II − 1)

In Gerald's program the **column index** of `TRAP` counts the halvings (column 1 = 10
subintervals, column I+1 = 10·2^I subintervals) and the **row index** is the extrapolation order
(row 1 = the trapezoidal rule itself). The program:

1. computes the trapezoidal rule with 10 subintervals on [0, B];
2. halves the step (at most 8 times, so at most 2560 subintervals). It reuses the running sum
   and only adds the new midpoints, so each halving costs as many function values as the
   previous total;
3. extrapolates the new column;
4. stops as soon as the last two entries of the newest column differ by no more than TOL:
   `IF (ABSF(TRAP(I+1,I+1) - TRAP(I,I+1)) - TOL) 50,50,20`.

The table is printed transposed: printed line L holds TRAP(1, L), …, TRAP(L, L). The first entry
of each line is a plain trapezoidal value, and the last is the best estimate so far.

The book's integrand is F(X) = SIN(X)/X, so the program computes the **sine integral** Si(B). Its
value at X = 0 is the limit 1, which the statement function cannot evaluate. The listing
therefore starts the sum with the literal `1.` in `SUM = 1. + FCN(B)`.

## The book's data card

The data card, read with `FORMAT (F10.0, E10.0)`, holds B and TOL:

```
15.0           2.E-7
```

The book's output:

```
VALUE OF SINE INTEGRAL BETWEEN 0 AND  15.00 BY ROMBERG INTEGRATION

1.6077255
1.6156591 1.6183036
1.6175654 1.6182008 1.6181940
1.6180369 1.6181940 1.6181936 1.6181936

VALUE IS  1.6181936,
  80 SUBINTERVALS WERE REQUIRED TO MEET TOLERANCE OF  2.0000000E-07
```

Read the table by columns:

* The first column (trapezoidal rule with 10, 20, 40, 80 subintervals) creeps toward the answer.
  Its error falls by a factor of about 4 per halving (h²).
* The last entry of each line is far better. Line 4 already agrees with Si(15) to 7 digits after
  only 80 subintervals.
* The test compares the last two entries of a line. Line 3 (1.6182008 vs 1.6181940) differs by
  6.8e-6 > TOL, so the program halves again. Line 4 (1.6181936 vs 1.6181936) meets TOL, so the
  run stops with K = 80 subintervals.

## Other outcomes the program handles

| Situation | Book output | Modern behaviour |
|---|---|---|
| TOL met after halving I | the I+1 lines, `VALUE IS …,` and `K SUBINTERVALS WERE REQUIRED TO MEET TOLERANCE OF …` | result, `converged = True`, `subintervals = 10·2^I` |
| TOL not met after 8 halvings | all 9 lines (line 9 wraps after 8 values) and `VALUE IS … BUT DID NOT MEET TOLERANCE OF …` | result, `converged = False`, value TRAP(9,9), 2560 subintervals (not an error) |
| F(X) is NaN or infinite (learner functions only) | — (impossible on the original machine) | `InputError` (trace code `INPUT`) |

Other integrands can be selected as presets: 2 = exp(−x²) and 3 = 1/(1+x²). Learners can also
type their own function on the Python engine. The sum is seeded with the function's own value at
0, and the book's `1.` is used for SIN(X)/X. The heading still says `SINE INTEGRAL`, because it
is the book's text.

## Precision

The book printed **1.6181936**; the real64 engines print **1.6181944** (1.6181944440409433), which
is the true Si(15) = 1.6181944437… to 7 decimals. Every value in the book's table is **low**, by
between 1e-7 (line 1) and 8.6e-7 (line 4). A modern single-precision build (`make
build-fortran-single`, IEEE binary32) also prints 1.6181944 (value 1.6181945). So the deficit is not
"single versus double precision". It comes from the arithmetic of the book's machine, which
**chopped** its results. The closest model is a 27-bit binary mantissa with chopping (the IBM
7090/7094 class; also the closest model for the Simpson program, `ch03_p01`): repeating the
computation that way gives 1.6181938 for the final value, within 3e-7 of the book (every entry of
its table is within 3e-7 too). It is not digit for digit, because that machine's own SINF routine is
not known; an 8-digit decimal chopped model (IBM 1620 class) gives 1.6181909. To re-run these
models, use `uv run python -m gerald_na.tools.book_machine` in `python/`. The book's computer is not
identified, and the Chapter 1 printouts point to a decimal machine (see `docs/architecture.md`, "The
book's computer"). Chopping always errs toward zero, so the errors accumulate over the 81 function
values instead of cancelling. IEEE arithmetic rounds to nearest and has no such bias.

All of these arithmetic models stop at the same place: line 4, 80 subintervals. The golden tests
therefore compare the table and the value within 1e-6 in both precisions, compare the
subinterval count exactly, and compare real64 bit for bit with its own values.

Precision also decides when TOL can be met at all. When the extrapolated values agree to the last
bit, the tested difference is **exactly zero** and any TOL ≥ 0 is satisfied. In real64 the book
card with TOL = 1.E-14 stops after 320 subintervals, as soon as that happens. In real32 it
happens much earlier: preset 3 with B = 100 and TOL = 1.E-13 does not converge in real64 but
does in real32. Try it with the Fortran `SINGLE` build.
